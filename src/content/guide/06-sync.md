<TLDR>

Код и данные живут в разных местах. Код ходит только через GitHub: поток пушит ветку, ноутбук делает `git pull`, хостинг публикует `main`. Твои задачи и клиенты лежат в браузере телефона, их нет на GitHub — поэтому экспорт и бэкап нужны с первого дня.

</TLDR>

## Код и данные — два разных пути {#code-vs-data}

**Код** — то, из чего сделано приложение: экраны, кнопки, логика «Выбери за меня». Его пишут <Term id="thread">потоки</Term>, он лежит в <Term id="repository">репозитории</Term> и меняется через <Term id="pull-request">PR</Term>.

**Данные** — то, что ты вносишь в приложение: задачи, привычки, клиенты, сессии фокуса. Их пишешь ты, пальцем на телефоне. Код одинаков у всех копий приложения, данные — только твои.

Эти две вещи путешествуют разными дорогами. Если их перепутать, легко потерять либо работу потока, либо месяц своих задач.

## Код: всё идёт через GitHub {#code-via-github}

У кода три места, где он бывает: облачный поток, твой ноутбук и хостинг. Ни одно из них не говорит с другим напрямую. Они встречаются только на GitHub — это единственная точка правды.

### Поток работает в своей копии {#thread-copy}

Облачный поток получает свою машину. Репозиторий клонируется в виртуальную машину Anthropic, поток работает там и пушит свою ветку на GitHub (проверено: октябрь 2026). Дальше он открывает PR, а ты делаешь <Term id="merge">мердж</Term> в `main`.

Пока ветка не запушена, работы потока нет нигде, кроме его машины. Ни ты, ни другой поток её не видите. Поэтому «готово» без запушенной ветки — это ещё не готово.

### Ноутбук забирает свежий main {#pull}

Если ты открываешь проект на ноутбуке, там лежит своя копия репозитория. Сама она не обновляется: после каждого мерджа её нужно подтянуть с GitHub командой `git pull`.

```bash
git switch main
# Already on 'main'
git pull
# Updating a655daa..e96e491
# Fast-forward
git log --oneline -1
# e96e491 Merge pick-for-me
```

Если ты ничего не правишь на ноутбуке, этот шаг не нужен вовсе. Для проекта с потоками ноутбук — необязательная копия, а не главное место.

Облачную сессию можно продолжить в терминале: `claude --teleport` скачивает и переключает ветку этой сессии (проверено: октябрь 2026). После этого локальная копия живёт отдельно от облачной, и встретятся они снова только на GitHub.

### Правки и на ноутбуке, и в потоке {#both-sides}

Если ты правишь что-то на ноутбуке, пока потоки работают в облаке, держись трёх привычек. Перед началом — `git pull`, чтобы начать со свежего `main`. Работай в своей ветке, а не прямо в `main`. Закончил — запушь ветку и открой PR, как поток.

Тогда твоя правка — просто ещё один PR среди прочих. Если поток в это время менял тот же файл, GitHub покажет <Term id="conflict">конфликт</Term>, и его решают так же, как в [«Git и GitHub»](/guide/05-git-github).

### Хостинг публикует main {#hosting}

Хостинг берёт код из `main` и выкладывает его в интернет. Телефон открывает приложение по ссылке и скачивает с хостинга свежую версию. Как это настроить, разбираем в [«Деплой»](/guide/12-deploy).

Отсюда простое правило: на телефон попадает только то, что слито в `main`. Ветка с недоделанным таймером фокуса до телефона не доедет, пока её PR не смерджен.

<Deeper title="Почему копии не видят друг друга">

Git распределённый: каждая копия репозитория хранит всю историю целиком и работает без связи с остальными. Поток, ноутбук и GitHub — три полноценные копии.

Синхронизация в Git всегда явная. `git push` отправляет новые <Term id="commit">коммиты</Term> из твоей копии на GitHub, `git pull` забирает чужие. Ничего не происходит само, поэтому GitHub и служит общей точкой встречи.

</Deeper>

## Песочница потока: коммить чаще {#commit-often}

**Песочница** — временная машина, где работает облачный поток. Она не вечная: облачная сессия останавливается после простоя, и её машина освобождается (проверено: октябрь 2026). При возвращении переписка восстанавливается, а запущенные команды — нет.

У потоков проекта песочница засыпает между ходами. Если продолжить её нельзя, поток начинает со свежей копии репозитория, и незакоммиченные изменения могут пропасть (проверено: октябрь 2026). Сохраняется только то, что поток закоммитил и запушил.

<Callout type="important" title="«Поток всё помнит — значит, и файлы на месте»">

Нет. Поток помнит разговор, но файлы живут на машине, которую могут забрать. Надёжно только то, что лежит в коммите на GitHub. Поэтому проси коммитить и пушить незаконченную работу после каждого шага.

</Callout>

Проще всего вписать это правило в <Term id="project-instructions">инструкции проекта</Term> один раз. Тогда его получит каждый поток, и тебе не придётся напоминать.

<PhraseCard
	title="Коммить незаконченное"
	when="Длинная задача в потоке или правило для инструкций проекта"
	text="После каждого законченного шага коммить и пушь работу в свою ветку, даже если задача не готова. В сообщении коммита пиши, что сделано и что осталось. Ничего не форсь и не пиши в main."
/>

### Как проверить, что всё сохранено {#check-saved}

Перед паузой или в конце длинной задачи спроси поток прямо. Ответ должен быть коротким: «всё закоммичено и запушено, ветка такая-то, последний коммит такой-то».

<PhraseCard
	title="Всё ли запушено"
	when="Перед паузой или концом сессии"
	text="Проверь git status в своей копии. Если есть незакоммиченные изменения, закоммить их в свою ветку с сообщением «WIP: что сделано, что осталось» и запушь. Пришли имя ветки и короткий хэш последнего коммита."
/>

Хэш потом легко найти на GitHub в списке коммитов ветки. Видишь его там — работа в безопасности, даже если машина потока исчезнет.

## Library хранит копии {#library-copies}

**Library** — вкладка проекта, где лежат файлы, которые ты добавил, и файлы, которые сделали потоки (проверено: октябрь 2026). Потоки читают их как обычные файлы.

Главное про Library: загрузка — это копия. Если ты поменял файл на компьютере, проект об этом не узнает, пока ты не загрузишь его снова и не выберешь **Replace** (проверено: октябрь 2026). Из добавленной папки проект берёт копию первых 100 файлов, до 200 МБ.

Значит, у одного файла легко появятся две версии: твоя на диске и старая в Library. Поток будет честно работать по старой.

<Callout type="tip" title="Живые документы — в репозиторий">

ТЗ, спеки модулей и заметки, которые меняются, держи в репозитории, например в папке `docs/`. Их правят потоки через PR, и версия всегда одна. В Library клади то, что не меняется: PDF, скриншоты, примеры.

</Callout>

Как заметить, что поток работает по старой копии? Попроси его процитировать дату или первую строку файла, по которому он работает. Если цитата не совпадает с твоей версией, загрузи файл заново.

Подробнее о том, какие файлы куда класть, — в [«Файлы проекта»](/guide/04-project-files).

## Данные живут на телефоне {#data-on-phone}

Твои задачи, клиенты и привычки хранятся прямо в браузере телефона. Для этого есть встроенная база **IndexedDB**: она лежит на устройстве и привязана к адресу сайта. На GitHub этих данных нет и быть не должно.

Так приложение открывается без сети и отвечает мгновенно: не нужно ждать сервер. А личное — номера клиентов, заметки после медитации — не покидает телефон.

У такого хранения есть обратная сторона. Данные есть только в одном браузере на одном устройстве:

- на ноутбуке то же приложение откроется пустым;
- очистка данных сайта или удаление приложения стирает всё;
- потерянный телефон — потерянные задачи, если нет бэкапа.

Синхронизация данных между устройствами — отдельная большая задача со своими ловушками. Её разбираем в [«Local-first»](/advanced/a1-local-first). Для первой версии хватит одного телефона и бэкапа.

### Обновление не трогает данные {#updates-keep-data}

Когда поток выпускает новую версию, телефон скачивает с хостинга новый код. Данные в IndexedDB при этом остаются на месте: код и данные лежат в разных хранилищах.

Опасный момент один — когда новая версия меняет форму данных. Например, модуль «Клиенты» добавляет к записи поле «следующий шаг». Тогда нужна миграция, и перед ней — свежий бэкап. Как это устроено, — в [«Архитектура приложения»](/guide/11-architecture#versions).

<Deeper title="Может ли браузер удалить данные сам">

Может. По умолчанию хранилище сайта «по возможности» (best-effort): при нехватке места браузер вправе его очистить. Сайт может попросить постоянное хранилище вызовом `navigator.storage.persist()`. Тогда данные удаляются, только если этого захочешь ты.

В Safari правило строже. Если с сайтом семь дней не было ни одного касания, Safari может удалить все данные, которые записали его скрипты. Ещё одна причина делать бэкап, даже если у тебя Android.

</Deeper>

<Callout type="danger" title="Не клади данные в репозиторий">

Не проси поток «сохранить мои задачи в GitHub» или закоммитить файл с клиентами. Репозиторий хранит историю вечно: телефон клиента останется в ней, даже если файл удалить. Подробнее — в [«Безопасность»](/guide/13-security).

</Callout>

## Экспорт и бэкап с первого дня {#backup}

**Экспорт** — кнопка, которая сохраняет все данные приложения в один файл. **Импорт** — обратная кнопка: загрузить такой файл и вернуть всё как было. Вместе они и есть твой бэкап.

Добавь их в первую же версию, ещё до таймера и привычек. Через месяц в приложении будут сотни задач, и терять их обиднее, чем пустой Inbox.

Хороший экспорт выглядит так:

- один файл JSON со всеми данными и номером версии схемы;
- дата в имени файла, например `second-brain-2026-10-23.json`;
- импорт сначала проверяет файл и только потом заменяет данные;
- в настройках видно, когда был последний бэкап.

<PhraseCard
	title="Экспорт и импорт"
	when="Первая версия приложения, до новых модулей"
	text="Добавь в настройки экспорт всех данных в один JSON-файл с датой в имени и номером версии схемы. Добавь импорт: он сначала проверяет файл и показывает, сколько записей загрузит, и только после подтверждения заменяет данные. Покажи дату последнего экспорта. Сделай это в новой ветке и открой PR."
/>

### Где хранить бэкап {#backup-place}

Файл бэкапа, который лежит только в памяти того же телефона, не спасёт от потери телефона. Его место — вне устройства.

- **Облачный диск.** Сохрани файл через системное меню «Поделиться» прямо в свой облачный диск.
- **Письмо себе.** Грубо, но работает: файл с датой в теме письма.
- **Ноутбук.** Если ты им пользуешься — отдельная папка с бэкапами, не внутри репозитория.

Раз в неделю достаточно. Напоминание может показывать сам экран Today: «последний бэкап — 9 дней назад».

Проверь бэкап хотя бы раз: экспортируй, открой приложение в другом браузере и импортируй файл. Бэкап, который ни разу не восстанавливали, — это надежда, а не бэкап.

Как устроен формат и что делать, когда схема данных меняется, — в [«Архитектура приложения»](/guide/11-architecture#versions).

## Шпаргалка: что где живёт {#cheatsheet}

| Что | Где живёт | Как не потерять |
| --- | --- | --- |
| Код в работе | Песочница потока | Коммит и push в ветку |
| Готовый код | GitHub, ветка `main` | Уже в безопасности |
| Копия кода у тебя | Ноутбук | `git pull` перед работой |
| ТЗ и спеки модулей | Репозиторий, папка `docs/` | Правки через PR |
| Справочные файлы | Library проекта | Заново загрузить после правки |
| Задачи, клиенты, привычки | Браузер телефона | Экспорт и бэкап |
| Бэкап | Облачный диск или почта | Проверить импортом |

Если сомневаешься, куда положить новую вещь, спроси себя: это то, из чего сделано приложение, или то, что ты в него вносишь? Первое идёт через GitHub, второе остаётся на телефоне и в бэкапах.

## Выводы {#takeaways}

<Takeaways>

- Код и данные живут в разных местах и ходят разными дорогами.
- Все копии кода — поток, ноутбук и хостинг — встречаются только на GitHub.
- Песочница потока временная, поэтому надёжно только то, что закоммичено и запушено.
- Library хранит копии: изменённый на компьютере файл нужно загрузить заново.
- Данные приложения лежат в браузере телефона, а не на GitHub, и в репозиторий не попадают.
- Экспорт и импорт нужны с первой версии, а бэкап нужно хотя бы раз восстановить.

</Takeaways>
