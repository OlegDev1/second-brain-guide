<TLDR>

Всё в приложении — одна и та же «запись» с пометкой о типе: задача, заметка, привычка или клиент. Как карточки в одной картотеке, только с разными ярлыками. Каждая часть приложения (модуль) живёт в своей папке со своим паспортом и своим описанием (ТЗ), а с другими частями общается только короткими сообщениями (событиями). Благодаря этому помощники работают над разными частями одновременно и не мешают друг другу, а 30 частей не превращаются в клубок.

</TLDR>

## Одна модель: запись {#item}

**Запись** (item) — единица данных второго мозга. Задача, заметка, привычка, клиент, цель, сессия фокуса, медитация — всё это записи, у которых разный тип. Поля у всех одни и те же.

```ts title="src/lib/items/types.ts"
export type ItemType = 'task' | 'note' | 'habit' | 'contact' | 'goal' | 'focus' | 'meditation';

export interface Item {
	id: string;
	type: ItemType;
	title: string;
	body?: string;
	status: 'inbox' | 'active' | 'done' | 'archived';
	createdAt: string;
	updatedAt: string;
	dueAt?: string;
	doneAt?: string;
	tags: string[];
	links: string[];
	data?: Record<string, unknown>;
}
```

`links` — это id связанных записей: звонок клиенту ссылается на клиента, задача — на цель. В `data` модуль кладёт свои особые поля: длительность сессии фокуса, номер телефона клиента, частоту привычки.

Одна модель упрощает три вещи сразу:

- **поиск** ищет по одной таблице и находит и задачу, и заметку, и клиента;
- **Inbox** принимает что угодно, а тип ты выбираешь потом, при разборе;
- **аналитика и экспорт** проходят по одному списку записей, а не по десяти разным.

Вот как одна запись проживает свою жизнь. В метро ты пишешь в Inbox «подарок маме» — появляется запись со статусом `inbox` и типом `note`. Вечером при разборе ты меняешь тип на `task`, ставишь срок на пятницу и тег «семья». Это всё та же запись с тем же `id`: ничего не копируется и не теряется.

Новый модуль не требует новой таблицы. Он просто добавляет тип записи и свои поля в `data`.

<Deeper title="Почему не отдельная таблица на каждый модуль">

Отдельные таблицы кажутся аккуратнее: у задачи свои колонки, у клиента свои. Но тогда поиску, Inbox, аналитике и экспорту нужно знать про каждую таблицу. Каждый новый модуль заставляет менять их все — и все потоки лезут в одни и те же файлы.

С одной таблицей общие части пишутся один раз. Цена — поля в `data` не так строго проверяются базой, поэтому каждый модуль проверяет их сам. Для личного приложения на десятки тысяч записей это хороший обмен.

</Deeper>

## Модуль — папка с паспортом {#module}

**Модуль** — одна функция приложения целиком: таймер фокуса, привычки, клиенты. Он живёт в своей папке `src/modules/<name>/`, и всё, что ему нужно, лежит там.

```text title="src/modules/focus/"
src/modules/focus/
├── manifest.ts         паспорт модуля
├── SPEC.md             ТЗ модуля
├── store.svelte.ts     состояние и работа с записями
├── FocusPage.svelte    экран /focus
├── TodayWidget.svelte  карточка на экране Today
└── Settings.svelte     настройки модуля
```

**Паспорт** (manifest) — короткий файл, который рассказывает приложению о модуле: имя, иконку, адреса экранов, виджет для Today и настройки.

```ts title="src/modules/focus/manifest.ts"
import type { ModuleManifest } from '$lib/modules';
import TodayWidget from './TodayWidget.svelte';
import Settings from './Settings.svelte';

export const manifest: ModuleManifest = {
	id: 'focus',
	name: 'Фокус',
	icon: 'timer',
	routes: ['/focus'],
	itemTypes: ['focus'],
	todayWidget: TodayWidget,
	settings: Settings
};
```

**Состояние модуля** живёт в `store.svelte.ts`: что сейчас на экране и как модуль меняет записи. Вот конец сессии фокуса целиком — запись в базу и событие для остальных:

```ts title="src/modules/focus/store.svelte.ts"
import { db } from '$lib/db';
import { emit } from '$lib/events';

export const focus = $state({ running: false, startedAt: 0 });

export async function finish() {
	const minutes = Math.round((Date.now() - focus.startedAt) / 60_000);
	const now = new Date().toISOString();
	const id = crypto.randomUUID();
	await db.table('items').add({
		id, type: 'focus', title: 'Сессия фокуса', status: 'done',
		createdAt: now, updatedAt: now, tags: [], links: [], data: { minutes }
	});
	focus.running = false;
	emit('focus:finished', { id, minutes });
}
```

Модуль фокуса не знает, кто ждёт его событие. Сегодня это аналитика, завтра — привычка «час фокуса в день». Ему не нужно меняться ни в первом, ни во втором случае.

Все паспорта собирает **реестр** — один список модулей. Меню, экран Today и настройки строятся по нему сами: добавил строку — модуль появился везде.

```ts title="src/modules/registry.ts"
import { manifest as inbox } from './inbox/manifest';
import { manifest as tasks } from './tasks/manifest';
import { manifest as focus } from './focus/manifest';

export const modules = [inbox, tasks, focus];
```

### Один поток — одна папка {#one-thread-one-folder}

Главный выигрыш модулей — параллельная работа. Поток, который делает привычки, правит только `src/modules/habits/`. Поток с таймером — только `src/modules/focus/`. Их PR не трогают одни и те же строки, и <Term id="conflict">конфликтов</Term> почти не бывает.

Общие файлы — модель записи, события, реестр — меняются редко и отдельной задачей. Как делить работу между потоками, разбираем в [«Команда агентов»](/guide/07-agent-team).

<Callout type="tip" title="ТЗ модуля лежит рядом с кодом">

`SPEC.md` в папке модуля — его маленькое <Term id="spec">ТЗ</Term>: что делает, какие записи создаёт, какие события шлёт и слушает. Поток читает его первым и обновляет в том же PR, что и код. Как писать такие ТЗ, — в [«ТЗ и промпты»](/guide/03-specs-prompts).

</Callout>

## Модули говорят событиями {#events}

**Событие** — сообщение «что-то произошло», которое модуль отправляет всем, кому интересно. Отправитель не знает, кто его слушает. Слушатели не знают, кто отправил.

Ты отметил задачу «Позвонить Ане» выполненной. Модуль задач шлёт событие `task:done`. Аналитика добавляет его в дневной счёт, привычка «Звонки клиентам» продлевает серию, а модуль задач об этом даже не знает.

```ts title="src/lib/events.ts"
type Events = {
	'task:done': { id: string; doneAt: string };
	'focus:finished': { id: string; minutes: number };
	'habit:checked': { id: string; date: string };
};

const bus = new EventTarget();

export function emit<K extends keyof Events>(name: K, detail: Events[K]): void {
	bus.dispatchEvent(new CustomEvent(name, { detail }));
}

export function on<K extends keyof Events>(name: K, handler: (detail: Events[K]) => void) {
	const listener = (event: Event) => handler((event as CustomEvent<Events[K]>).detail);
	bus.addEventListener(name, listener);
	return () => bus.removeEventListener(name, listener);
}
```

Модуль задач вызывает `emit('task:done', …)`, аналитика и привычки подписываются через `on('task:done', …)`. Список событий в одном месте — это и документация: видно, кто о чём может сообщить.

Правило простое: модуль никогда не импортирует код другого модуля. Он работает с записями через ядро, сообщает о своих делах событиями и слушает чужие события. Тогда любой модуль можно выключить, и остальные продолжат работать.

## Модули второго мозга {#modules-map}

Вот все функции из твоего списка, разложенные по модулям и волнам. **MVP** — первая версия, без которой приложение бесполезно. **v1** — то, ради чего ты его затеял. **v2** — когда первые две волны уже живут неделями.

| Модуль | Что делает | Волна |
| --- | --- | --- |
| Inbox | Быстрая запись за секунду, разбор потом | MVP |
| Задачи | Списки, сроки, таблицы с фильтрами | MVP |
| Today | Цели дня и задачи на сегодня | MVP |
| Фокус | Таймер фокуса, сессии пишутся в записи | v1 |
| «Выбери за меня» | Задача под твоё время и энергию | v1 |
| Привычки | Отметки, серии и пропуски | v1 |
| Медитация | Одна кнопка: таймер и запись сессии | v1 |
| Клиенты | Кому позвонить, следующий шаг, напоминание | v1 |
| Аналитика | Разбор дня и вечерний обзор | v2 |

**Inbox** — самый важный экран. Мысль должна попадать туда за пару секунд: открыл, написал, закрыл. Голос сначала идёт через диктовку клавиатуры телефона; своё распознавание речи — задача на потом.

**Today** не хранит ничего своего. Он собирает виджеты модулей по реестру: цели дня, задачи на сегодня, таймер фокуса, привычки, кого набрать.

### «Выбери за меня» {#pick-for-me}

Кнопка для момента «не знаю, за что взяться». Ты говоришь, сколько у тебя времени и сколько сил, а приложение выбирает одну задачу. Выбор случайный, но с весами: срочное и важное выпадает чаще.

```ts title="src/modules/pick/pick.ts"
export function pickForMe(tasks: Task[], freeMinutes: number, energy: Energy): Task | undefined {
	const fit = tasks.filter((t) => t.minutes <= freeMinutes && t.energy <= energy);
	const weights = fit.map((t) => 1 + urgency(t) + (t.important ? 2 : 0));
	let roll = Math.random() * weights.reduce((sum, w) => sum + w, 0);
	return fit.find((_, i) => (roll -= weights[i]) < 0);
}
```

Сначала фильтр: только задачи, которые влезают в свободные минуты и не требуют больше сил, чем есть. Потом у каждой вес: база 1, плюс срочность по сроку, плюс 2 за важность. Задача с весом 6 выпадает в шесть раз чаще задачи с весом 1 — но и та иногда выпадет, поэтому мелочи не гниют вечно.

### Привычки: серии и пропуски {#habits}

Привычка — запись типа `habit`, а каждая отметка — дата в её `data`. **Серия** — сколько дней подряд привычка отмечена. Её не хранят, а считают из дат: тогда серия не может «разъехаться» с отметками.

Пропуск — тоже информация. Экран привычки показывает не только серию, но и пропуски за месяц: «пропустил два раза подряд» — сигнал важнее, чем «серия 40 дней». Привычки слушают события: `focus:finished` может сам отметить привычку «час фокуса».

### Клиенты: кому позвонить {#clients}

Клиент — запись типа `contact`. В `data` лежат телефон, дата последнего контакта и следующий шаг. Экран «Кому позвонить» сортирует клиентов по тому, как давно ты с ними говорил и когда назначен следующий шаг.

Номер — ссылка `tel:`: на телефоне касание открывает набор номера. После звонка одна кнопка записывает контакт и спрашивает следующий шаг с датой.

Напоминание «позвонить в 15:00» — самая капризная часть. Чистая PWA не гарантирует точное время, поэтому этот модуль идёт вместе с Capacitor — подробно в [«Стек и скорость»](/guide/10-stack-speed#android).

### Аналитика и вечерний обзор {#analytics}

Аналитика ничего не спрашивает у других модулей. Она слушает события — `task:done`, `focus:finished`, `habit:checked` — и считает день: сколько сделано, сколько минут фокуса, какие привычки отмечены.

Вечерний обзор — экран из трёх вопросов: что получилось, что нет, что главное завтра. Ответы становятся записью-заметкой, а главное на завтра — целью на экране Today следующего утра. Тяжёлые подсчёты за месяцы уходят в воркер, чтобы экран не замирал.

## Версии схемы и миграции {#versions}

**Схема** — форма данных: какие поля есть у записи и по каким база умеет искать. Она будет меняться: модуль «Клиенты» добавит поля, аналитике понадобится новый индекс. Каждое изменение — новая **версия схемы**.

**Миграция** — код, который переводит старые записи в новую форму. Dexie делает это встроенно: ты объявляешь новую версию и функцию обновления, а при следующем запуске база обновится сама.

```ts title="src/lib/db.ts"
import Dexie from 'dexie';

export const db = new Dexie('second-brain');

db.version(1).stores({ items: 'id, type, status, dueAt, *tags' });

db.version(2)
	.stores({ items: 'id, type, status, dueAt, updatedAt, *tags' })
	.upgrade((tx) =>
		tx.table('items').toCollection().modify((item) => {
			item.updatedAt ??= item.createdAt;
		})
	);
```

Версия 2 добавляет индекс по `updatedAt`, а миграция заполняет это поле у старых записей. Если миграция падает, Dexie откатывает её целиком, и данные остаются в старой версии.

Три правила для миграций:

- старые версии в коде не удаляются и не меняются, добавляется только новая;
- поле сначала перестают использовать, а удаляют отдельной версией позже;
- перед каждым выпуском с новой версией — экспорт на телефоне.

<Callout type="danger" title="Миграция без бэкапа">

Миграция работает с настоящими данными на телефоне. Ошибка в ней может испортить записи, которые не вернуть ничем, кроме бэкапа. Перед обновлением схемы сделай экспорт и проверь миграцию на копии своих данных.

</Callout>

### Экспорт и импорт в JSON {#export}

Экспорт — один файл со всеми записями и номером версии схемы. Зачем он нужен с первого дня, — в [«Синхронизация»](/guide/06-sync#backup).

```json title="second-brain-2026-10-23.json"
{
	"app": "second-brain",
	"schemaVersion": 2,
	"exportedAt": "2026-10-23T18:30:00Z",
	"items": [
		{
			"id": "a1",
			"type": "task",
			"title": "Позвонить Ане",
			"status": "done",
			"createdAt": "2026-10-20T09:00:00Z",
			"updatedAt": "2026-10-23T15:00:00Z",
			"tags": ["клиенты"],
			"links": []
		}
	]
}
```

Импорт читает `schemaVersion` и прогоняет старый файл через те же шаги миграции. Поэтому бэкап полугодовой давности тоже загрузится в новую версию приложения.

## Ядро — это мало кода {#core}

**Ядро** — общая часть, на которую опираются все модули. Оно должно быть маленьким и меняться редко:

- модель записи и база данных;
- шина событий и список событий;
- реестр модулей;
- экспорт, импорт и миграции;
- общие компоненты интерфейса и настройки.

Всё остальное — в модулях. Если поток хочет добавить в ядро «временно, только для привычек», это сигнал, что место этому коду в модуле привычек.

Через 30 модулей архитектура ломается не сразу, а по одному импорту. Раз в несколько волн проси поток проверить правила.

## Порядок сборки {#build-order}

Модули строятся не все сразу, а по одному: каждый следующий опирается на предыдущие.

1. **Каркас, запись, Inbox и задачи.** Модель записи, база, события, реестр и первые два модуля. С этого дня приложением можно пользоваться.
2. **Today.** Собирает виджеты и цели дня — заодно проверяет, что реестр работает.
3. **Фокус.** Первый модуль, который шлёт событие и пишет свои записи.
4. **«Выбери за меня».** Опирается на задачи с временем и энергией.
5. **Привычки.** Первые слушатели событий: серии растут сами.
6. **Клиенты.** Требует Capacitor ради точных напоминаний.
7. **Аналитика.** Последней: ей нужны события от всех остальных.

Медитацию можно вставить в любой момент после Today: она маленькая и ни от кого не зависит. Шаг 1 — работа одного потока, дальше по одному потоку на модуль, по два параллельно.

## Выводы {#takeaways}

<Takeaways>

- Всё в приложении — одна запись с типом, поэтому поиск, Inbox, аналитика и экспорт пишутся один раз.
- Модуль — папка `src/modules/<name>/` с паспортом, своим ТЗ и своим состоянием, а реестр собирает все модули.
- Модули не импортируют друг друга и общаются только событиями, поэтому любой можно выключить.
- Один поток работает в одной папке модуля, и параллельные PR почти не конфликтуют.
- Схема данных меняется версиями с миграциями, а перед каждой миграцией нужен экспорт.
- Строим по порядку: каркас и Inbox, Today, Фокус, «Выбери за меня», Привычки, Клиенты, Аналитика.

</Takeaways>
