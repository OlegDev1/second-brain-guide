<TLDR>

Деплой — это публикация: готовый код с GitHub уходит туда, где приложение работает. Простой сайт без своей базы данных кладут на GitHub Pages, и каждое принятое изменение (мердж) в главную версию (`main`) — новая версия по той же ссылке. Если нужна база данных, одного Pages мало: серверную часть держат, например, на Cloudflare. Всё, что попало в код сайта, видит любой посетитель, поэтому секретным ключам там не место.

</TLDR>

## Деплой — из GitHub к тебе {#what-is-deploy}

<Term id="deploy">Деплой</Term> — шаг, после которого код начинает работать. Пока код лежит в <Term id="repository">репозитории</Term>, это просто файлы. Чтобы открыть приложение и нажать кнопку, его нужно куда-то выложить: на сервер в интернете или на твоё устройство.

В проекте деплой — последнее звено цепочки из [«Синхронизация»](/guide/06-sync#code-path). Ты пишешь ТЗ, поток делает работу и приносит её в `main` через PR. А деплой берёт свежий `main` и публикует его. Настраивают его один раз, дальше он идёт сам после каждого <Term id="merge">мерджа</Term>.

## Три варианта {#options}

Выбор зависит от одного вопроса: нужен ли приложению свой сервер с базой данных.

**1. Статический сайт — GitHub Pages.** Статический — значит, сайт состоит только из страниц, стилей и скриптов, которые работают в браузере. Своей базы на сервере у него нет. GitHub Pages как раз такой хостинг: он только отдаёт файлы (проверено: октябрь 2026). Он лежит там же, где код, и на нём стоит этот сайт. «Второму мозгу» Pages подходит, пока данные хранятся в браузере на устройстве.

**2. Нужна база данных — Cloudflare Workers.** Pages — это только фронтенд, то есть то, что видишь на экране. Хранить общие данные или выполнять код на сервере он не умеет. Для этого нужна серверная часть — бэкенд. Её можно разместить, например, на Cloudflare Workers: это платформа для серверного кода, и у Cloudflare рядом есть своя база данных D1 (проверено: октябрь 2026).

**3. Фронтенд у себя, бэкенд на Cloudflare.** Фронтенд можно вообще не публиковать: скачать его с GitHub на своё устройство и запускать у себя. А за данными он обращается к бэкенду на Cloudflare. Так в интернете открыт только бэкенд, а сам интерфейс есть только у тебя.

Не знаешь, что выбрать, — начни с первого варианта. Если позже понадобится база, поток добавит бэкенд, а сайт можно оставить на Pages.

<Callout type="important" title="«Репозиторий приватный — значит, и сайт закрыт»">

Нет. Сайт на GitHub Pages открыт всему интернету, даже если репозиторий приватный (проверено: октябрь 2026). А на бесплатном плане GitHub Pages работает только с публичными репозиториями; для приватного нужен GitHub Pro или Team. Твоих данных в репозитории нет, поэтому сайт их не раскрывает.

</Callout>

## Первый деплой на GitHub Pages {#first-deploy}

Деплой на Pages идёт через GitHub Actions — встроенный в GitHub запуск задач. При каждом обновлении `main` GitHub сам собирает сайт и публикует его. Файл с этими шагами пишет поток, тебе остаются две кнопки в настройках.

<Steps>
	<Step title="Поток готовит деплой" check="в PR есть файл в папке .github/workflows">

Попроси поток фразой ниже. Он добавит файл с шагами сборки и откроет PR.

	</Step>
	<Step title="Включи Pages из Actions" check="в Source выбрано GitHub Actions">

На GitHub открой репозиторий → **Settings** → **Pages**. В блоке **Build and deployment** выбери в **Source** вариант **GitHub Actions**.

	</Step>
	<Step title="Смерджи PR" check="PR в статусе Merged">

Мердж в `main` и есть команда «опубликуй». Сборка запустится сама.

	</Step>
	<Step title="Дождись зелёной галочки" check="на вкладке Actions зелёная галочка у последнего запуска">

Открой вкладку **Actions**. Красный крестик — открой запуск, скопируй ошибку и отдай потоку.

	</Step>
	<Step title="Открой ссылку" check="сайт открывается по адресу https://твой-логин.github.io/имя-репозитория/">

Ссылка видна там же, в **Settings** → **Pages**. Пройдись по главным экранам: стили на месте, переходы не ведут на 404.

	</Step>
</Steps>

	title="Первый деплой"
	when="Приложение собирается, а ссылки ещё нет"
	text="Настрой деплой на GitHub Pages через GitHub Actions: сборка из main, адрес сайта с именем репозитория. Скажи, что мне включить в Settings → Pages. Открой PR."
/>

Если сайт открылся без стилей или ссылки ведут на 404, скорее всего, сборка не знает, по какому адресу лежит сайт. Это частая мелочь: отдай её потоку со скриншотом.

Свой домен, например `brain.example.ru`, подключают в **Settings** → **Pages** → **Custom domain**. Остальное подскажет поток.

## Что в сайте видно всем {#env}

Код сайта скачивает каждый посетитель. Значит, всё, что попало в код, публично: адреса, настройки, тексты. Это касается и значений, которые подставляют при сборке, а не пишут в код прямо.

Что можно: адрес своего бэкенда, название приложения, номер версии. Что никогда: ключи платных сервисов, токены, пароли. Им место в секретах бэкенда, например на Cloudflare; как это устроено, разобрано в [«Безопасность»](/guide/13-security#keys).

## Выводы {#takeaways}

<Takeaways>

- Деплой берёт свежий `main` с GitHub и выкладывает его туда, где приложение работает; настраивают его один раз.
- Статический сайт без своей базы данных идёт на GitHub Pages, и каждый мердж — новая версия по той же ссылке.
- GitHub Pages — только фронтенд: если нужна база данных, бэкенд держат отдельно, например на Cloudflare Workers.
- Фронтенд можно запускать у себя на устройстве, а с бэкендом на Cloudflare он общается сам.
- Сайт на GitHub Pages открыт всем, даже из приватного репозитория, поэтому в его коде не бывает ключей.

</Takeaways>
