<TLDR>

Git — это программа, которая хранит каждую версию проекта, как цепочку сохранений в игре (коммитов). GitHub держит эту цепочку в интернете, чтобы она не потерялась и была доступна отовсюду. Каждый помощник работает в своей отдельной копии (ветке) и не мешает остальным, а готовую работу приносит в главную версию (`main`) через заявку на проверку (PR). Если что-то сломалось, ошибку отменяют новым сохранением (revert): старая история остаётся целой, ничего не пропадает.

</TLDR>

## Git и GitHub: история и облако {#git-vs-github}

**Git** — программа, которая хранит историю папки проекта: каждую версию, которую сохранили. Она знает, что поменялось, когда и кто это сделал. Если что-то сломалось, Git помнит, как было до этого.

**GitHub** — сайт, где эта история лежит в облаке. Папка проекта вместе со всей историей называется <Term id="repository">репозиторий</Term>. У твоего «второго мозга» он один: в нём Inbox, задачи, таймер фокуса и всё остальное. В любом другом проекте так же: один проект — один репозиторий.

Как это связано с проектом в Claude. Ты не работаешь с Git руками: это делают <Term id="thread">потоки</Term>. Каждый поток берёт копию репозитория с GitHub, делает свою задачу и отправляет результат обратно. Твоя часть — посмотреть, что он сделал, и решить, принимать ли это.

Какую проблему это решает. Несколько агентов правят один проект одновременно, и без истории их работа перемешалась бы. Git держит работу каждого отдельно, показывает, кто что поменял, и позволяет вернуть любую прошлую версию.

Создавай репозиторий приватным: при создании выбери **Private**. Приватный репозиторий видишь только ты и те, кому ты дал доступ. Публичный может открыть любой человек.

Сначала разберём основы: коммит, ветку, PR и мердж. Этого хватает для повседневной работы. Squash, rebase, reset и теги лежат в свёрнутом блоке [«Продвинутое»](#advanced) в конце главы, его можно пропустить.

## Коммит — снимок с подписью {#commit}

{null}<Term id="commit">Коммит</Term> — сохранённый снимок всех файлов проекта в один момент. К снимку прикреплены сообщение, автор и время. Коммиты выстраиваются в цепочку: каждый знает, какой был перед ним. Эта цепочка и есть история.

Сообщение отвечает на вопрос «что изменилось»: `Add focus timer`, `Fix pause in focus timer`. Потоки пишут сообщения сами, а ты по ним потом находишь нужный момент.

Коммит — снимок всего проекта, а не правка одного файла. Поэтому к любому коммиту можно вернуться целиком: и Inbox, и таймер будут такими, какими были в ту минуту.

### Хэш — номер коммита {#hash}

У каждого коммита есть <Term id="hash">хэш</Term> — уникальный номер из цифр и букв от a до f. Полный хэш длинный, 40 символов, но обычно хватает первых семи, например `d7bd791`. Именно короткий хэш ты увидишь на GitHub и в отчётах потоков.

Хэш — твой способ точно сказать агенту, о каком моменте речь: «верни как было в `ac97c1d`». Подделать старый коммит незаметно нельзя: хэш считается из содержимого, и любая правка меняет его.

## Ветка — своя линия работы {#branch}

{null}<Term id="branch">Ветка</Term> — отдельная линия коммитов внутри одного репозитория. Создать ветку — значит сказать: «дальше я работаю отдельно, от вот этой точки». Коммиты в новой ветке копятся сами по себе, а главная версия в это время не меняется.

Главная ветка называется `main`. В ней лежит рабочая версия приложения: та, которой ты пользуешься и которая уходит на <Term id="deploy">деплой</Term>. Всё новое сначала делают в отдельной ветке и только потом приносят в `main`.

Вот как это выглядит на примере «второго мозга»:

<CommitGraph caption="Время идёт сверху вниз. Кружок — коммит. Зелёная линия — main, фиолетовая — ветка потока." />

Как читать схему, сверху вниз:

1. В `main` два коммита: экран Inbox и таймер фокуса. Это рабочая версия.
2. Поток получил задачу «Выбери за меня» и начал от таймера свою ветку — фиолетовую линию.
3. В ветке он сделал два коммита: кнопку и пояснение к ней. В `main` их пока нет: если открыть приложение, кнопки ещё не будет.
4. Работа готова, и ветку влили в `main` через PR #3. Теперь кнопка есть и в рабочей версии.
5. Дальше кто-то поставил фокус на 50 минут — это ошибка, красный кружок. Следующий коммит её отменяет. Как это работает, разберём в разделе [про откат](#rollback).

### Зачем каждому потоку своя ветка {#thread-branch}

Каждый поток в проекте начинает новую ветку от `main` и работает только в ней (проверено: октябрь 2026). Один поток делает «Выбери за меня», другой — напоминания о звонках клиентам. Они не видят черновиков друг друга и не портят друг другу файлы.

Их работа встречается только в `main` и только через PR. Если поток сделал ерунду, его ветку просто не вливают, и `main` остаётся чистым. Как координатор раздаёт задачи потокам, разобрано в главах [«Проект»](/guide/02-project) и [«Команда агентов»](/guide/07-agent-team).

## PR — «моя ветка готова» {#pull-request}

{null}<Term id="pull-request">Пул-реквест</Term>, или PR, — сигнал «моя ветка готова, влейте её в `main`». Его открывает тот, кто работал в ветке. В проекте это почти всегда поток: он закончил свою фичу и сообщает координатору, что хочет влить работу в `main`.

Когда PR открывают:

- поток сделал задачу, закоммитил и запушил ветку — и открывает PR;
- проверяющий поток посмотрел ветку другого потока, ошибок нет — и открывает PR для неё;
- ты сам поправил что-то в ветке — тоже через PR, как поток.

PR — главное место проверки: всё, что поменял поток, видно до того, как оно попадёт в рабочую версию. В проекте карточка PR появляется прямо в потоке, с кнопками вроде **Merge it** и **Resolve conflicts** (проверено: октябрь 2026). На GitHub у PR три вкладки:

- **Conversation** — описание задачи, комментарии и отзывы.
- **Files changed** — дифф: какие строки добавлены, какие удалены.
- **Checks** — автоматические проверки, например сборка.

### Мердж — вливание ветки в main {#merge}

{null}<Term id="merge">Мердж</Term> — вливание одной ветки в другую. Когда PR проверен, ты нажимаешь на GitHub **Merge pull request** или **Merge it** на карточке в потоке. Коммиты ветки переходят в `main`, и сверху появляется отдельный коммит-мердж: «здесь влили PR #3».

После мерджа ветка своё дело сделала. Следующий поток начнёт свою ветку уже от обновлённого `main`, где есть работа предыдущего. Другие способы влить ветку, squash и rebase, — в блоке [«Продвинутое»](#merge-methods).

## Конфликт: две правки в одном месте {#conflict}

{null}<Term id="conflict">Конфликт</Term> случается, когда две ветки по-разному поменяли одно и то же место в одном файле. Например, один поток назвал экран задач «Мои задачи», а другой — «Задачи на сегодня». Git не знает, какой вариант тебе нужен, и останавливается.

Git помечает в файле оба варианта, один под другим. Разрешить конфликт — значит оставить нужный вариант или собрать из двух один, а пометки убрать. Кто это делает:

- **Поток.** Когда у PR потока конфликт, на его карточке может появиться кнопка **Resolve conflicts**. Она отправляет потоку это поручение от твоего имени, и он разбирается в своей ветке (проверено: октябрь 2026).
- **Ты на GitHub.** Кнопка **Resolve conflicts** внизу PR открывает редактор прямо на сайте. Он справляется только с простыми случаями. Сложное отдай потоку.

Сам поток конфликт может не заметить: GitHub не присылает событие, когда `main` уехал вперёд и появился конфликт (проверено: октябрь 2026). Поэтому нажать кнопку или написать «разреши конфликт с `main`» — твоя часть работы.

Лучшая защита от конфликтов — делить задачи так, чтобы потоки трогали разные файлы. Как это делать, разобрано в главе [«Команда агентов»](/guide/07-agent-team).

## Почему main под защитой {#protected-main}

`main` — единственный источник правды. Из него собирается приложение, от него потоки начинают новые ветки. Сломан `main` — сломано всё, что от него зависит.

Поэтому два правила:

1. В `main` попадает только то, что прошло через PR.
2. В `main` никогда не делают force push — принудительную перезапись истории. Почему он опасен, разобрано в блоке [«Продвинутое»](#reset).

Облачные потоки `main` сами не охраняют. Их связь с GitHub не даёт удалять ветки, но не ограничивает, в какую ветку можно пушить (проверено: октябрь 2026). Поэтому впиши правило в <Term id="project-instructions">инструкции проекта</Term> (Project settings → Memory → Project instructions) — с них начинает каждый поток (проверено: октябрь 2026):

<PhraseCard
	title="Правило для инструкций проекта"
	text="Никогда не пушь в main напрямую и никогда не делай force push. Любое изменение — только через PR в новой ветке. Не мерджи без моего OK."
	when="Один раз, при настройке проекта"
/>

Инструкция — договорённость, а не замок: поток ей следует, но это не жёсткая настройка (проверено: октябрь 2026). Настоящий замок — правило защиты ветки (branch protection rule) на GitHub: оно запрещает force push и удаление ветки. Но на бесплатном плане GitHub оно работает только в публичных репозиториях, а для приватных нужен план Pro, Team или Enterprise.

## Как читать историю {#history}

История на GitHub отвечает на три вопроса: что поменялось, кто это сделал и когда. Открой репозиторий и нажми на число коммитов над списком файлов — откроется список коммитов ветки. Каждая строка в нём выглядит примерно так:

<CommitRow />

Нажми на строку — увидишь дифф этого коммита: добавленные строки отмечены плюсом, удалённые — минусом. Ещё два места, которые пригодятся:

- **История файла** — только коммиты, которые меняли этот файл. Удобно, когда ищешь, в какой момент сломался таймер.
- **Blame** — кнопка над файлом. Рядом с каждой строкой видно, каким коммитом, кем и когда она поменяна последней.

Пример: в таймере стоит 50 минут, а ты такого не просил. Открой файл, нажми **Blame** — рядом со строкой будет коммит `d7bd791 Make focus 50 minutes`. Теперь ты знаешь, что откатывать.

## Откат: ничего не теряется {#rollback}

Главная мысль главы: в Git почти ничего не теряется. Любой коммит, попавший в `main`, можно найти и вернуть.

<Callout type="important" title="Частая ошибка">

«Откат стирает всё, что было после него» — это неправда про обычный откат. Так работает только `reset` вместе с force push. Обычный откат — revert — ничего не стирает: он добавляет новый коммит, который отменяет старый.

</Callout>

### Revert — отмена новым коммитом {#revert}

{null}<Term id="revert">Откат коммитом (revert)</Term> создаёт новый коммит, который делает ровно обратное старому. Старый коммит остаётся в истории, рядом появляется его отмена. Если передумаешь, отмену тоже можно отменить.

Пример со схемы: кто-то поставил фокус на 50 минут, а тебе нужно 25. Поток делает revert коммита `d7bd791`, и в истории появляется новый коммит `Revert "Make focus 50 minutes"`. Ошибочный коммит на месте, но его изменения отменены. Команды набирать не нужно: их выполняет поток.

### Откат PR кнопкой на GitHub {#revert-pr}

Если плохим оказался целый PR, его можно откатить без терминала. GitHub создаст новый PR, который отменяет старый, а тебе останется его влить.

### Как попросить агента {#ask-agent}

Команды помнить не нужно. Достаточно назвать коммит, способ и рамки. Главная фраза этой главы:

<PhraseCard
	title="Безопасный откат"
	text="Откати изменения после abc1234 через revert в новой ветке, открой PR, ничего не форсь."
	when="Что-то сломалось, и ты знаешь последний хороший коммит"
/>

Каждая часть закрывает свой риск:

- «после `abc1234`» — точная граница: всё, что было раньше, остаётся.
- «через revert» — история целая, откат можно отменить.
- «в новой ветке, открой PR» — ты увидишь изменения до того, как они попадут в `main`.
- «ничего не форсь» — прямой запрет на force push.

Вместо `abc1234` подставь хэш последнего хорошего коммита. Найди его в списке коммитов на GitHub или через **Blame**.

## Ключ попал в репозиторий {#leaked-key}

Если в коммит попал пароль или API-ключ, сначала отзови его в сервисе, который его выдал, и выпусти новый. Revert и удаление файла не помогут: ключ останется в старых коммитах. Что делать дальше, разобрано в главе [«Безопасность»](/guide/13-security#leak).

## Продвинутое {#advanced}

Здесь то, что нужно реже: другие способы мерджа, точечные откаты, reset и теги. Для повседневной работы хватит основ выше, а этот блок пригодится, когда поток упомянет что-то из этого в отчёте.

<Accordion title="Открыть: squash, rebase, reset, теги">

### Squash и rebase: другие способы мерджа {#merge-methods}

На GitHub у кнопки мерджа есть стрелка с тремя вариантами:

- **Create a merge commit** — обычный мердж из основ: коммиты ветки плюс коммит-мердж.
- **Squash and merge** — все коммиты ветки склеиваются в один коммит в `main`. Одна задача — один коммит: его легко найти и отменить.
- **Rebase and merge** — коммиты ветки встают в `main` по одному, без коммита-мерджа.

Для проекта подойдёт любой. Ещё слово rebase встречается в отчётах потоков в другом смысле: «сделал rebase на свежий `main`». Это значит, что поток переставил свою ветку так, будто начал её от сегодняшнего `main`. Так часто разрешают конфликт в своей ветке.

### Вернуть один файл {#restore-file}

Бывает, что сломан один файл, а всё остальное в новых коммитах нужно. Тогда поток берёт только этот файл из старого коммита и сохраняет его новым коммитом. История целая: видно, что файл вернули и откуда.

	when="Сломан один файл, остальные изменения нужны"
/>

### Посмотреть старую версию {#old-version}

Хочешь просто посмотреть, как было неделю назад? Попроси поток создать ветку от старого коммита. `main` при этом не меняется, поэтому сломать ничего нельзя. Откатить `main` такой веткой не выйдет: для этого нужен revert.

<PhraseCard
	title="Посмотреть старую версию"
	text="Создай ветку от коммита ac97c1d, чтобы я мог посмотреть проект таким, как тогда. В main ничего не меняй."

### Reset и force push — крайний случай {#reset}

Reset переставляет ветку назад, на старый коммит. Коммиты после него из ветки пропадают. Чтобы так же поменять ветку на GitHub, нужен force push — принудительная перезапись. Это допустимо только в собственной ветке с черновиками, где больше никто не работает.

<Callout type="danger" title="Force push переписывает историю">

Force push заменяет ветку на GitHub твоей версией, и коммиты, которых нет в твоей копии, из неё пропадают — даже чужие. Никогда не делай его в `main` и в ветке, где работает кто-то ещё. Сомневаешься — бери revert.

</Callout>

Вернуть коммиты после reset иногда можно, но только из той копии репозитория, где его делали. Копия облачного потока исчезает вместе с его машиной после простоя (проверено: октябрь 2026), так что на это не рассчитывай.

### Теги и релизы — точки сохранения {#releases}

Тег — закладка, которая никогда не двигается. Её ставят на важный коммит и дают имя: `v0.1`, `v0.2`. Релиз на GitHub — это тег плюс описание и архив кода на тот момент: «вот версия, которая точно работала».

Поставить первый: на главной странице репозитория справа нажми **Releases**, потом **Draft a new release**. В **Choose a tag** впиши `v0.1` и нажми **Create new tag**, проверь, что в **Target** стоит `main`, и нажми **Publish release**. Облачный поток тег на GitHub не отправит, его связь с GitHub пропускает только ветки (проверено: октябрь 2026).

### Код в другом проекте {#reuse}

Чтобы начать похожий проект, включи у репозитория **Template repository** в настройках: новый репозиторий получит те же файлы с чистой историей. Если берёшь чужой код, проверь файл `LICENSE`: без лицензии копировать код без разрешения автора нельзя.

</Accordion>

## Выводы {#takeaways}

<Takeaways>

- Git хранит историю как цепочку коммитов-снимков, GitHub держит её в облаке, а потоки работают с ней за тебя.
- Ветка — своя линия работы: каждый поток делает задачу в своей ветке, и `main` не меняется, пока ветку не влили.
- PR — сигнал «моя ветка готова»: поток открывает его, когда закончил фичу, а ты проверяешь и вливаешь.
- `main` — источник правды: только PR и никакого force push. Правило впиши в инструкции проекта.
- Revert — откат по умолчанию: новый коммит отменяет старый, ничего не теряется.
- «Откат стирает всё после» — это про reset с force push, а не про revert.

</Takeaways>
